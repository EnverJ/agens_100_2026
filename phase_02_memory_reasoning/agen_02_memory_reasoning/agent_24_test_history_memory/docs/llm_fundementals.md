# LLM Fundamentals: Agent 24 — Test History Memory

- **Metadata filtering vs. semantic search — knowing when to use each**: Semantic search answers "find me things similar to this description." Metadata filtering answers "give me all records where field X equals value Y." Agent 24 uses metadata filtering as its primary access pattern because the caller always knows the exact test_name they want to inspect. Semantic search is secondary — it comes into play only if the caller wants to find tests with similar error messages across different test names. Understanding which access pattern fits the use case is one of the most important design decisions in any vector-store application.

- **When keyed lookup beats similarity search**: For entities with stable, exact identifiers (test names, user IDs, document IDs), metadata-keyed lookup is faster, more precise, and simpler than similarity search. Similarity search adds value when identifiers are unknown, ambiguous, or expressed in natural language. In Agent 24, the test name is always known exactly at query time, so metadata filtering is the right primary mechanism. Similarity search would be correct if someone asked "find tests similar to the auth redirect test" — a different query pattern handled by Agent 23.

- **Embedding test error messages for cross-test similarity**: Even though Agent 24's primary access pattern is keyed lookup, the text document stored alongside each entry includes the error message. This means the collection supports a secondary query mode: "find all test outcomes with errors similar to this error message." This allows an agent to discover that test_payment_gateway_timeout and test_checkout_session_expired both produce TimeoutError variants, even though they are different tests. The embedding of the error message is what makes this cross-test discovery possible.

- **ChromaDB where clause for metadata filtering**: ChromaDB's `where` parameter accepts a dict of filter conditions that are applied before the k-NN search runs, narrowing the candidate set. For Agent 24, the where clause `{"test_name": {"$eq": target_test_name}}` restricts retrieval to only the entries for that specific test. This is efficient because ChromaDB indexes metadata separately from the vector index, so the metadata filter runs without touching the vector space at all.

- **Ordering retrieved results by recency**: ChromaDB does not natively sort results by a metadata timestamp field — it sorts by similarity distance. For Agent 24's primary use case (retrieve the N most recent outcomes for a named test), the agent must fetch more results than needed, then sort by the timestamp metadata field client-side before taking the top N. This is a common pattern in hybrid retrieval: use the vector store for filtering and recall, use Python for ordering and formatting.
