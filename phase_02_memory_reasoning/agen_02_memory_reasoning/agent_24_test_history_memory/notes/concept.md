# Concept: Per-Test History Memory

Agent 24 exists to answer the question that Agent 23 cannot: "what happened specifically to this one test, across every time it has run?" Agent 23 stores suite-level summaries — a single entry per test run that captures aggregate counts and the top failure messages for the entire suite. That granularity is useful for suite-level trend questions, but it loses the individual test signal. If test_login_oauth_redirect failed in a suite of 200 tests, its failure is a footnote in the Agent 23 entry. Agent 24 makes that individual test the primary unit of memory.

The architectural difference between Agent 23 and Agent 24 comes down to how ChromaDB metadata is used. Both agents use the same embedding-and-upsert backbone from Agent 22. What differs is the metadata schema and how retrieval is scoped. Agent 24 stores every individual test outcome as its own ChromaDB entry, with `test_name` as a required metadata field on every entry. When a query arrives for "test_login_oauth_redirect", the agent uses ChromaDB's metadata `where` clause to pre-filter by `test_name` before running the similarity search. This is keyed retrieval: the test name is the key, and metadata filtering is how you look up by key in a vector store.

This metadata-keyed retrieval pattern is important to understand because it reveals when to use semantic search and when to use metadata filtering. Semantic search is the right tool when you do not know the exact identifier of what you want — you describe what you're looking for and let similarity find it. Metadata filtering is the right tool when you know the exact identifier and want all records associated with it. Agent 24 uses the latter: the caller always knows which test they want to inspect. The semantic component still matters — the embedded text (the error message, the outcome description) makes it possible to find related tests by meaning — but the primary access pattern is keyed by test_name.

The downstream value of Agent 24 becomes clear when Agent 37 (Flaky Test Detector) runs. To classify a test as flaky, it needs the outcome history for that specific test: did it pass sometimes and fail other times under identical conditions? Agent 24 provides exactly that retrieval — the N most recent outcomes for a named test, ordered by recency. Without per-test memory, a flaky test detector would have to re-parse run logs or maintain its own state. With Agent 24, it simply queries the memory layer and receives structured outcome history ready for analysis.
