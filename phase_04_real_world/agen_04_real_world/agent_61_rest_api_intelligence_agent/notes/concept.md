# Concept: REST API Intelligence Agent

Agent 61 represents the shift from mechanical API testing to intelligent API evaluation. Traditional API tests check status codes and maybe assert a specific field value. But real API failures in production rarely announce themselves with a 500 error — they arrive as subtly wrong data: a price returned as a string instead of a float, a user object missing the `roles` field under certain account states, a pagination cursor that is always null. These failures pass every naive assertion while silently breaking downstream consumers.

The core innovation here is using an LLM as the evaluator. When you provide an API contract — even a loose English description like "this endpoint returns an order object with order_id, status, items array, and total_price" — the LLM can read the actual response and assess it against that contract with nuanced judgment. It can identify when a field is present but has a semantically wrong value (e.g., `status: "CMPLTD"` instead of a documented enum), when an array is unexpectedly empty in a context where it should have items, or when response time metadata suggests a performance regression.

This agent also introduces the pattern of wrapping an external HTTP call inside an agent. The `requests` library becomes the "tool" that the agent uses to gather evidence, and the LLM then reasons over that evidence. This separation — tool call for data acquisition, LLM for judgment — is a recurring pattern across the rest of phase 4 and beyond. Agents 66 (Jenkins), 72 (Allure), and 78 (JMeter) all use the same pattern with different data sources.

Connecting to Agent 60, which introduced structured agent output, Agent 61 takes that output discipline further: the LLM must return a verdict, a confidence level, and an itemized list of findings. This forces the LLM to be specific about what it found rather than generating an unstructured narrative, making the agent's output usable by downstream agents in a pipeline.
