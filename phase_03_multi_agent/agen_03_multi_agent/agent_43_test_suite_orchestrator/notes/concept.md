# Concept — Agent 43: Test Suite Orchestrator

CI/CD pipelines and agent orchestration solve the same fundamental problem: how do you coordinate a sequence of distinct steps that each depend on the previous step succeeding? In a traditional CI/CD system, this coordination is expressed as YAML configuration (GitHub Actions, Jenkins pipelines) or shell scripts. The steps are rigid — changing the pipeline requires editing configuration files, and observability is limited to log output. When you express the same pipeline as agent orchestration, each step becomes a callable agent with defined input/output contracts, and the pipeline controller (the orchestrator) becomes a program that can reason about what to do next. The logic becomes inspectable, testable, and modifiable at the code level.

A test plan decomposes naturally into agent calls because a test plan is already a structured sequence of groups with defined scope, dependencies, and success criteria. Smoke tests run first because they validate the environment — if smoke tests fail, nothing else will work. Unit tests run before integration tests because failures at the unit level indicate problems that would cause integration tests to fail for the wrong reasons. Each group has a distinct scope and can be delegated to an agent specialized for that group. The orchestrator's job is to manage this sequence: call the right agent for each group, collect its result, decide whether to continue, and eventually hand off everything to the report generator.

"Abort-on-critical-failure" is a specific type of conditional logic in the orchestration: after a designated critical test group runs, the orchestrator checks its result before deciding whether to proceed. If smoke tests fail (meaning the environment is broken), continuing to run unit tests and integration tests against a broken environment produces meaningless results — the agent would collect a long list of failures that are all caused by the same root issue, not by actual code defects. Abort-on-critical-failure prevents this noise. As agent logic, this is straightforward: after calling the smoke test agent, check the returned result; if `critical_failure: true`, set `abort = True` and skip all remaining test group calls, passing the partial results directly to the report generator with a note that the suite was aborted.

This agent connects to Agent 32 (test plan generator): Agent 32 produces the structured test plan that Agent 43 consumes. In a complete system, Agent 32 runs first to generate the test plan from requirements or a feature spec, and Agent 43 runs next to execute that plan. Together they form a two-stage pipeline: plan generation followed by plan execution. Agent 43 does not know or care how the test plan was created — it only requires that the test plan conform to the expected input schema. This separation allows the test plan generator and the test suite orchestrator to evolve independently.
