# LLM Fundamentals — Agent 43: Test Suite Orchestrator

- **Test plan parsing via LLM**: The test plan may arrive as a structured JSON document, a semi-structured text file, or a mix of both. An LLM call can normalize a messy test plan into the expected schema — extracting test group names, identifying which groups are critical, and inferring execution order from descriptions. This is preferable to writing brittle regex parsers for every possible test plan format.

- **Abort decision logic**: The orchestrator uses an LLM call (or a deterministic rule) to evaluate whether a critical group failure should trigger an abort. For simple cases (smoke test failed → abort), a deterministic rule is sufficient. For nuanced cases (40% of unit tests failed but the failures are all in deprecated modules → do not abort), an LLM can evaluate the failure context and recommend whether to abort or continue. This is an early example of an LLM as a decision node in a pipeline, not just a text generator.

- **Result aggregation prompt**: After all test groups have run, the orchestrator passes all group results to the report generator agent via a structured prompt. The aggregation prompt must include the full result set (all groups, their individual counts, and any abort context) so the report generator can produce an accurate and complete report. The prompt design here follows the same principles as Agent 41's aggregation call: provide all results simultaneously, not one at a time.

- **Structured output contracts for test results**: Each test execution agent must return results in a consistent schema so the orchestrator can accumulate them without custom parsing for each agent type. Enforcing a shared output schema across all test execution agents is a prompt engineering requirement: each agent's system prompt must specify the exact JSON structure it must return. Without consistent schemas, the orchestrator cannot reliably sum counts across groups.

- **LLM as pipeline controller**: In this agent, the LLM is not just generating text — it is making pipeline control decisions (continue vs abort, which group to run next if the plan is ambiguous). This is a key conceptual shift: an LLM call can return a decision that changes what the next line of code does, making it a genuine control flow participant rather than a passive text processor embedded in otherwise deterministic logic.
